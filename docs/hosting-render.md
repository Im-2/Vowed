# Hosting the backend on Render (free web service)

Goal: a public HTTPS address that a judge's APK can reach. Everything here uses free tiers and devnet test keys. **You** create the account and type the secrets into Render's dashboard; nothing below asks you to paste a secret anywhere else, and nothing is deployed until you do it.

## What the free tier means for this backend (read first)

- **The disk is temporary.** A deploy or a restart wipes it, and a service idle for 15 minutes is stopped and starts again (about 50 seconds to wake) with an empty disk. The database lives at `/tmp/vowed.sqlite`.
- **Rebuilt from the chain on every start** (tested in `backend/test/restart-recovery.test.ts`): all pools, joins, check-ins and settlements (the indexer now reads the program's whole history in pages when the database is empty), and the **sample public challenges** (recognised again by their plan hash, so Explore keeps its titles).
- **Not rebuilt (lost on a wipe):** squads, invites, feed and nudges; registered phone proof keys; plans and goal text of players' own pools (the chain keeps only a hash, so their titles show as generic until the app re-uploads); faucet claim history (so the once-a-day limit resets); reports; the AI answer cache.
- **What to do about it:** keep the service awake with a free monitor (step 7), so it is not wiped by idling; avoid redeploying shortly before judging; after any wipe, testers open the app and tap Disconnect, then connect again (this re-registers the phone's proof key). A durable database (a small external store) is a possible later step; say if you want it.
- Free instances get 750 hours a month, enough for one service to run all month.

## Step by step

1. **Account.** Go to https://render.com and choose "Get Started". Sign up with GitHub (simplest). A card is not asked for free web services; if it is, stop and tell me.
2. **Connect the repo.** In the Render dashboard: New + > Blueprint > "Connect a repository" > install/authorise Render's GitHub app for `Im-2/Vowed` (only that repository is enough) > pick it.
3. **Blueprint.** Render reads `render.yaml` at the repo root: service `vowed-backend`, plan Free, root directory `backend`, build `npm ci --include=dev` (the server runs through `tsx`, a dev dependency), start `npx tsx src/index.ts`, health check `/v1/health`. It then asks for the values marked secret (next step). Public settings (devnet, RPC, jobs on, `SEED_TARGET=4`, database path) are already filled in.
   If you prefer the manual route: New + > Web Service > the repo, Runtime Node, Root Directory `backend`, Build Command `npm ci --include=dev`, Start Command `npx tsx src/index.ts`, Instance Type Free, Health Check Path `/v1/health`, and add every variable below.
4. **Create the values file on your PC (nothing is printed):**
   ```
   cd backend
   npx tsx scripts/render-env.ts
   ```
   This writes `backend/.devnet/render-env.txt` (git-ignored; one `NAME=value` per line). Open it in Notepad.
5. **Type each value into Render** (Environment page, "Add Environment Variable", or the prompts from the Blueprint): copy the part after the `=` into the matching name. Never paste them into chat.

   | Name | Where it comes from |
   |---|---|
   | `JWT_SECRET` | freshly generated by the script (64 hex characters); only Render will have it |
   | `ORACLE_SECRET_KEY` | the **new oracle key** (`backend/.devnet/oracle.json`), rotated on chain on 2026-10-07 with `update_oracle`; the old oracle can no longer record check-ins. It can ONLY call `record_checkin` |
   | `CRANK_SECRET_KEY` | `backend/.devnet/crank.json`: pays fees to settle pools, holds no authority and almost no SOL |
   | `SEED_SECRET_KEY` | `backend/.devnet/seeder.json`: throwaway key that creates the sample challenges; holds the SOL for their rent |
   | `FAUCET_AUTHORITY_SECRET_KEY` | the **dedicated faucet key** (`backend/.devnet/faucet.json`). It is the mint authority of the two test tokens and holds 0.05 devnet SOL for new token accounts, nothing else. The deployer key (program upgrade authority and admin) is **never** put on Render |
   | `REWARDS_SECRET_KEY` | `backend/.devnet/rewards.json`: the throwaway wallet that holds the test SKR for the weekly rewards and receives streak-freeze payments (holds 0.02 devnet SOL and test SKR only). Without it the rewards and perks screens say they are off |
   | `FAUCET_USDC_MINT`, `FAUCET_SKR_MINT` | public mint addresses of the two test tokens (not secret) |
   | `GEMINI_API_KEY` | optional; from `backend/.devnet/gemini-key.txt`. Render's network may reach Google when your PC cannot. Leave it out and the template matcher still works |

   Already set by `render.yaml` (public): `NODE_VERSION=24`, `NETWORK=devnet`, `RPC_URL`, `RUN_JOBS=true`, `AUTH_DOMAIN=vowed.app`, `SEED_TARGET=4`, `DATABASE_PATH=/tmp/vowed.sqlite`.
6. **Deploy and check.** Click Create / Deploy. When the log says the service is live, open `https://<your-service>.onrender.com/v1/health`; it should show `{"ok":true,...,"network":"devnet","jobs":true,"db":true}`. Give it two minutes: the first start reads the chain history and, after about 90 seconds, tops up the sample challenges.
7. **Keep it awake.** Free account at https://uptimerobot.com > Add New Monitor > HTTP(s) > URL = the health address > interval 5 minutes. (A health request every 5 minutes is well under the free hours.)
8. **Tidy up.** Delete `backend/.devnet/render-env.txt` and clear your clipboard history. Tell me the service URL (it is public, not a secret) and I will build the APK with `.\gradlew.bat assembleDebug -PbackendUrl=https://<your-service>.onrender.com`.

## Costs on devnet

Each sample challenge locks about 0.005 SOL of rent. `SEED_TARGET=4` keeps four open at a time and tops up as their 24-hour join windows end: roughly 0.02 SOL a day. The seeder holds 0.1 SOL, so about five days; the health of that wallet is logged (`sample-challenge wallet is low on SOL`). Top up with `npx tsx scripts/seeder-setup.ts --sol 0.1` (plain transfer from the deployer, never a faucet).

## Key separation (done once with `backend/scripts/rotate-keys.ts`)

- Deployer: stays on this PC. Program upgrade authority and admin; signs nothing on the host.
- Faucet key: new; the mint authority of both test mints was moved to it (a plain SPL `SetAuthority`), funded with 0.05 SOL from the deployer.
- Oracle key: new; `update_oracle` was signed by the admin (deployer); the old oracle's remaining SOL was moved to the new one.
- What a leak on the host would allow: minting test tokens (worthless), recording false check-ins for pools (devnet), spending the small SOL balances. It could not upgrade the program or change the config.
